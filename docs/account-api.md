# API личного кабинета · F5 · серверный этап

Реализовано 02.11.2026. Новое дополнение к API; существующий контракт витрины в `docs/api-contract.md` не изменён. Интерфейс ЛК и подключение реального SMS-провайдера — следующие шаги.

Дальнейшие этапы, включая Яндекс/VK ID и бонусы, описаны в [сводном плане реализации v2](superpowers/plans/2026-11-02-account-loyalty-v2.md). Данный документ описывает фактически реализованный API входа по коду; внешние ID пока не подключены.

## Область действия

Вход по подтверждённому российскому телефону, профиль и только новые заказы, оформленные через авторизованный endpoint. Старые заказы и любые гостевые заказы не переносятся в ЛК, даже при совпадении телефона. Маршрутов привязки истории нет.

Имя и email можно редактировать, телефон — только читать. Email не используется как подтверждённый канал входа. Данные уже оформленных заказов остаются снимком на момент покупки. Статусы берутся из имеющихся записей сайта; получение новых статусов из 1С не входит в этот этап. Бонусы реализуются по отдельному [плану интеграции](project-plan.md).

## Включение и отправка SMS

По умолчанию `ACCOUNT_ENABLED=0`, новые маршруты отсутствуют. Для включения нужны:

| Настройка          | Значение                                                                                                                                             |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ACCOUNT_ENABLED`  | `1`                                                                                                                                                  |
| `ACCOUNT_ORIGINS`  | Разрешённые origin витрины через запятую, например `https://avenuefashion.online,https://www.avenuefashion.online`; без завершающего `/` и без путей |
| `AUTH_CODE_SECRET` | Отдельный случайный секрет длиной не менее 32 символов из менеджера секретов                                                                         |
| `DATABASE_URL`     | PostgreSQL; обязателен для production                                                                                                                |
| `NODE_ENV`         | `production` для рабочего сервера                                                                                                                    |

Кроме окружения, в `buildApp({ smsSender })` передаётся адаптер провайдера, реализующий `SmsSender` из `packages/backend/src/auth/types.ts`:

```typescript
interface SmsSender {
  kind: 'test' | 'provider';
  send(phone: string, code: string): Promise<void>;
}
```

`send` завершается после принятия сообщения провайдером или бросает исключение. Адаптер обязан ограничивать время HTTP-запросов к провайдеру и не логировать телефон/код/ключи доступа. Конкретный поставщик и реализация сетевого адаптера пока не выбраны. Штатный `src/index.ts` адаптер не передаёт: одним переключателем окружения включить рабочую отправку нельзя, запуск завершится явной ошибкой до создания приложения.

Тестовый отправитель внедряется только в тестах. Режима выдачи кода через HTTP, фиксированного кода или вывода кода в консоль нет. В production проверяется наличие PostgreSQL и `kind: 'provider'`, память для авторизации не допускается.

Таблицы из `019_accounts.sql` создаются идемпотентно при первом обращении к репозиторию. Миграцию можно предварительно применить вручную; существующая `014_orders.sql` уже содержит `user_id`, миграции старых заказов не требуется. Существующие гостевые строки остаются с `user_id = NULL`.

## Правила запросов браузера

- Для всех запросов к API ЛК использовать `credentials: 'include'`.
- Каждый изменяющий запрос (`POST`/`PATCH`) требует `Origin` из `ACCOUNT_ORIGINS` и `X-FA-Account: 1`.
- JSON-запросы требуют `Content-Type: application/json`. Максимальное тело — 32 КБ.
- Изменения профиля, создание заказа и выход дополнительно требуют `X-FA-CSRF`, полученный после входа или через `GET /api/account/me`.
- Сервер устанавливает cookie `__Host-fa_session` с `Secure; HttpOnly; SameSite=Lax; Path=/`, без `Domain`, сроком 30 дней. Cookie принадлежит хосту API. В браузере необходим HTTPS; при разработке допускается HTTP-origin localhost, но проверять работу cookie следует на HTTPS.
- Все ответы ЛК имеют `Cache-Control: no-store` и `Vary: Origin`. Разрешённому origin возвращаются точный `Access-Control-Allow-Origin` и `Access-Control-Allow-Credentials: true`.
- Для витрины на другом поддомене того же сайта cookie отправляется с `credentials: 'include'`. Размещение витрины на другом регистрируемом домене требует отдельного решения; текущая cookie-политика ориентирована на один сайт.
- `OPTIONS /api/auth/*` и `OPTIONS /api/account/*` возвращают `204` для разрешённого origin. Заголовки: `content-type, x-fa-account, x-fa-csrf, idempotency-key`.
- Без сессии закрытые маршруты возвращают `401`, для чужого или отсутствующего заказа — одинаковый `404`.

## Вход и выход

### `POST /api/auth/code`

```json
{ "phone": "8 (913) 123-45-67" }
```

Ответ `202`:

```json
{ "challengeId": "случайный UUID v4", "expiresIn": 300, "resendAfter": 60 }
```

Телефон приводится к `+7XXXXXXXXXX` по существующим правилам заказов. Случайный шестизначный код хранится в виде HMAC с отдельным секретом. Действует 5 минут и не более 5 неверных попыток. Новая отправка отменяет прежний запрос. Коды из неуспешной отправки не активируются.

Ограничения в общем хранилище: повторная отправка не ранее чем через 60 секунд; не более 5 отправок на телефон и 20 на IP за часовое окно. При `429` возвращается `Retry-After: 60`; повтор может оставаться недоступен до конца часового окна. Ошибки провайдера не отменяют учёт отправок.

### `POST /api/auth/verify`

```json
{ "challengeId": "UUID из запроса кода", "code": "123456" }
```

Ответ `200`, установка cookie:

```json
{
  "account": {
    "id": "1",
    "phone": "+79131234567",
    "name": null,
    "email": null,
    "createdAt": "2026-11-02T12:00:00.000Z"
  },
  "csrfToken": "64 шестнадцатеричных символа"
}
```

Первый успешный вход создаёт аккаунт; последующие используют тот же аккаунт по телефону. Код потребляется атомарно вместе с созданием сессии. Одновременно подтвердить один код дважды нельзя. Случайный 32-байтный токен сессии выдаётся только в cookie, в БД хранится SHA-256. Предыдущая cookie-сессия этого браузера при успешном новом входе отзывается.

### `POST /api/auth/logout`

Без тела. Требуются cookie, Origin, `X-FA-Account` и `X-FA-CSRF`. Ответ `204`, сессия отозвана в БД, cookie очищена. Повтор с уже отозванной сессией получает `401`.

## Профиль

### `GET /api/account/me`

Ответ `200`: `{ "account": { ... }, "csrfToken": "..." }`, структура аккаунта как после входа. Можно использовать для восстановления интерфейса и подстановки имени/email/телефона в оформление.

### `PATCH /api/account/me`

```json
{ "name": "Анна Петрова", "email": "Anna@Example.Test" }
```

Хотя бы одно поле: имя 2–100 символов, email до 254 символов. Пробелы по краям удаляются, email приводится к нижнему регистру. `null` очищает соответствующее поле. Управляющие символы, неизвестные поля, изменение телефона или ID отклоняются. Ответ `200`: `{ "account": { ... } }`.

## Заказы аккаунта

### `POST /api/account/orders`

Тело, денежные единицы и проверка товара совпадают с `POST /api/orders` из действующего контракта. Дополнительно требуются сессия и CSRF. `Idempotency-Key` обязателен.

Владелец всегда определяется из сессии; поля `userId` из тела не используются. Телефон в заказе — контакт покупателя/получателя, он не меняет аккаунт и не определяет принадлежность заказа.

Ответ `201` (повтор — `200` с `Idempotent-Replayed: true`) имеет прежний публичный состав заказа, включая секретный токен для страницы «Спасибо». Повтор ключа с другим владельцем или из гостевого оформления возвращает `409 IDEMPOTENCY_KEY_REUSED`, данные заказа не выдаются. Обычный повтор с тем же владельцем возвращает тот же заказ даже после изменения каталога.

Гостевой `POST /api/orders` продолжает создавать гостевые заказы; cookie сама по себе не переводит его в режим ЛК. При подключении интерфейс должен явно выбирать авторизованный endpoint.

### `GET /api/account/orders?limit=20&offset=0`

Ответ `200`: `{ "orders": [...], "limit": 20, "offset": 0 }`. Сортировка: новые сначала, затем ID по убыванию. `limit` — 1–100, `offset` — 0–1 000 000. Строки содержат публичный состав заказа без секретного токена, контактов и адреса. Выборка только по владельцу `user_id`; поиск по телефону отсутствует.

### `GET /api/account/orders/:number`

`number` имеет вид `FA-12345678`. Ответ `200`: публичный состав без секретного токена, дополненный:

```json
{
  "customer": { "name": "Анна", "phone": "+79131234567", "email": "anna@example.test" },
  "delivery": { "method": "cdek", "city": "Омск", "address": "Улица, 1", "pvzCode": null },
  "comment": null
}
```

Показываются сохранённые данные конкретного заказа. Если номер отсутствует или принадлежит другому аккаунту — `404 ORDER_NOT_FOUND`.

## Ошибки

Новые ошибки ЛК: `{ "error": "КОД" }`. Ошибки оформления сохраняют прежние `message`, `fields`, `items` и суммы из контракта заказов.

| HTTP | Код                                  | Значение                                                  |
| ---- | ------------------------------------ | --------------------------------------------------------- |
| 400  | `INVALID_JSON`                       | Некорректный JSON                                         |
| 400  | `IDEMPOTENCY_KEY_REQUIRED`           | Не задан корректный ключ создания заказа                  |
| 401  | `UNAUTHENTICATED`                    | Нет действующей сессии                                    |
| 401  | `INVALID_CODE`                       | Код неверен, истёк, использован или исчерпал попытки      |
| 403  | `ORIGIN_FORBIDDEN`                   | Недопустимый origin либо отсутствует клиентский заголовок |
| 403  | `CSRF_INVALID`                       | Отсутствует или неверен CSRF-токен                        |
| 404  | `ORDER_NOT_FOUND`                    | Заказ недоступен этому аккаунту                           |
| 409  | `IDEMPOTENCY_KEY_REUSED`             | Ключ уже использован другим запросом/владельцем           |
| 413  | `PAYLOAD_TOO_LARGE`                  | Превышен размер тела                                      |
| 415  | `UNSUPPORTED_MEDIA_TYPE`             | Для JSON-маршрута передан другой формат                   |
| 422  | `INVALID_PHONE` / `VALIDATION_ERROR` | Некорректные поля                                         |
| 429  | `RATE_LIMITED`                       | Превышены ограничения                                     |
| 503  | `SMS_UNAVAILABLE`                    | Отправка сообщения не удалась                             |
| 503  | `ORDERS_DISABLED`                    | Приём заказов отключён                                    |
| 500  | `INTERNAL_ERROR`                     | Ошибка без внутренних подробностей                        |

## Проверка

```bash
npm run build -w @fa/backend
npm run lint
npm test
```

Только на отдельной тестовой PostgreSQL:

```bash
TEST_DATABASE_URL=postgresql://... npm test -w @fa/backend -- test/auth-pg.test.ts test/account-orders-pg.test.ts
```

Новые PG-тесты создают и удаляют собственные случайные схемы. Проверяются гонки кодов и ограничений, сохранение сессий/владельца, согласия, отсутствие гостевой истории, снимки заказа и выгрузка. Проверки без `TEST_DATABASE_URL` явно пропускаются.

Основа мер защиты: [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html). Разделение публичных и закрытых маршрутов использует [изоляцию плагинов Fastify](https://fastify.dev/docs/latest/Reference/Encapsulation/).
