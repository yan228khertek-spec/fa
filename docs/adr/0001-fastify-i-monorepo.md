# ADR-0001: HTTP-фреймворк приёмника CommerceML и структура монорепо

**Статус:** Принято
**Дата:** 06.10.2026
**Решали:** Ян + Клод (подтверждено Яном)

## Контекст

Приёмник обслуживает штатный «Обмен с сайтом» 1С:Розница 2.3: POST-файлы чанками до сотен МБ (zip с каталогом и картинками), ответы — plain text в байт-точном формате, Basic auth, далее потоковый парсинг XML в PostgreSQL. Стек по договору — Node.js + TypeScript. Команда — два разработчика, сроки сжатые.

## Решение

**Fastify** как HTTP-фреймворк. Монорепо на npm workspaces: `packages/backend` (приёмник + API витрины), `packages/frontend` (React/TS, пока заглушка); общий tooling — ESLint, Prettier, vitest, docker-compose с PostgreSQL 16.

## Рассмотренные варианты

### A: Fastify (выбран)

Потоковый приём тела из коробки (`addContentTypeParser` с raw-stream — чанки от 1С пишутся на диск, не задерживаясь в памяти); первоклассный TypeScript; явный контроль Content-Type и тела ответа — просто отдавать байт-точный plain text; встроенные лимиты размера тела и таймауты. Минус: менее привычен, чем Express.

### B: Express

Максимальная привычность, много примеров. Минусы: body-parser по умолчанию буферизует тело — стриминг требует обходить умолчания на конкретных роутах (типичный источник багов «файл обрезался»); TypeScript через внешние типы.

## Ключевой трейдофф

Главный технический риск слоя — приём сотен МБ чанками без распухания памяти и порчи байтов. Fastify делает это штатно и явно, Express — через обход собственных умолчаний. Привычность Express этого не перевешивает: протокольной логики немного, цена ошибки в стриминге высокая.

## Последствия

Проще: стриминг файлов, точные ответы, типизация, лимиты/таймауты. Сложнее: полдня на освоение Fastify тому, кто его не трогал. Пересмотр — только если упрёмся в несовместимость нужного middleware (маловероятно).
