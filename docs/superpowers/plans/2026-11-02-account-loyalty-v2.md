# Личный кабинет, вход и бонусная система — Implementation Plan v2

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Запустить личный кабинет Fashion Avenue с удобным входом, новыми заказами и подключением к действующей бонусной системе магазина.

**Architecture:** Существующий сервер Fastify и PostgreSQL обслуживают единый аккаунт магазина. Способы входа подключаются к этому аккаунту; отдельный модуль лояльности обращается к установленному при обследовании источнику баланса. Сначала выпускается базовый ЛК, затем чтение бонусов, затем операции по заказам.

**Tech Stack:** Node.js >=22, TypeScript, Fastify 5, PostgreSQL 16, Vitest; интерфейс интегрируется с согласованными исходниками витрины.

**Дата:** 02.11.2026. **Версия:** 2. **Статус:** актуальный сводный план в репозитории. Решения пользователя и рекомендации разработчика разделены ниже; план не означает подключения всех рассмотренных способов входа.

## Global Constraints

- Сначала сервер и API ЛК, затем интерфейс — согласовано пользователем.
- Сервиса отправки кодов пока нет — предусмотреть подключение.
- Старые гостевые заказы сайта не переносим и не привязываем, в том числе по совпадению телефона.
- В ЛК показываем только новые заказы, оформленные через авторизованный endpoint; гость продолжает оформлять покупки без обязательной регистрации.
- Исключение старых заказов сайта не исключает подключения существующих участников бонусной программы и чтения их действующего баланса из основной системы.
- Единый баланс для сайта и кассы. Отдельный независимо рассчитываемый бонусный баланс сайта не создаём.
- Пороги уровней, срок жизни бонусов, курс бонуса, правила списания и момент начисления берутся из согласованных правил программы, а не из предположений.
- Ни клиентский `userId`, ни фамилия, ни самостоятельно введённый телефон не подтверждают право на аккаунт или бонусы.
- SMS-коды, cookie, секреты провайдеров и данные доступа к CRM не попадают в репозиторий, публичные ответы и логи.
- Существующий публичный контракт витрины сохраняется. Дополнения к общему API согласуются между разработчиками согласно `docs/api-contract.md`.
- Реализация идёт в ветках `codex/` с проверками и PR. Оценка следующих этапов уточняется после получения необходимых данных; обследование само по себе не разрешает платные подключения или отправку сообщений.

## 3. Вход: целевая схема

Один внутренний аккаунт магазина может иметь несколько привязанных способов входа. Кнопки Яндекс, VK и подтверждение телефона должны открывать один и тот же профиль и новые заказы, когда привязка уже установлена.

### Сценарий внешнего входа

1. Покупатель выбирает Яндекс ID или VK ID.
2. Сервер проверяет ответ провайдера и получает разрешённые данные. Подлинность данных не определяется результатом, присланным браузером без серверной проверки.
3. Уже привязанный внешний идентификатор открывает существующий аккаунт магазина.
4. Для первой привязки проверяем доступность полного телефона и согласованный уровень его подтверждения. Если телефона нет или такого подтверждения недостаточно, предлагаем подтверждение нужного номера отдельным каналом.
5. При совпадении с существующим аккаунтом выполняем согласованное подтверждение привязки. Аккаунты не объединяются по имени, фото или email.
6. После завершения выдаётся обычная сессия магазина; при следующих входах подтверждение телефона повторяется только в предусмотренных правилами случаях, а не автоматически каждый раз.

Текущая таблица `customer_accounts` требует уникальный непустой телефон. Для первого выпуска сохраняем этот инвариант: до завершения подтверждения номера внешний вход может оставаться незавершённым, полноценный аккаунт без телефона не создаём. Возможность отдельного профиля без телефона — самостоятельное расширение, не часть текущего объёма.

### Яндекс ID

- Официально заявлено, что расходы на авторизационные уведомления берёт на себя Яндекс.
- Получение телефона требует соответствующего права; `default_phone` документирован как контактный телефон аккаунта. Проверку актуального владения SIM-картой этим полем автоматически не подменяем.
- До реализации проверяем доступные права, верификацию приложения и реальные ответы в тестовом сценарии.

### VK ID

- Официальный SDK предусматривает запрос `phone email` и вход через VK ID.
- Полный телефон, доступность полей нашему приложению и коммерческие условия необходимо подтвердить. Бесплатность всей интеграции и гарантированную передачу телефона клиенту пока не обещаем.

### Вход по телефону

- Реализованный сценарий: случайный шестизначный код, срок 5 минут, 5 неверных попыток, ограничение отправок на телефон и IP; сессия на 30 дней.
- При выборе обычного SMS подключаем реальный `SmsSender` к точке запуска.
- Flash Call и операторская авторизация могут возвращать свой код или отдельное подтверждение. Они требуют изменения сценария авторизации; их нельзя подключить как простую отправку произвольного шестизначного SMS.
- При нескольких каналах новый запрос отменяет или завершает прежний по явному правилу. Резервная отправка должна учитывать общие ограничения и расходы.

| Сотрудники магазина работают в 1С                           | Что именно 1С рассчитывает основной бонусный баланс                                               |
| Программа связана с CRM заказчика                           | Что известны название CRM, схема обмена или наличие API                                           |

## 5. Архитектура и границы модулей

| Область кода                                | Ответственность                                             | Изменения по плану                                                                     |
| ------------------------------------------- | ----------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `packages/backend/src/auth/`                | Проверка входа и сессии                                     | Реальный отправитель; выбранные внешние ID; подтверждение и привязка телефона          |
| `packages/backend/src/account/`             | Профиль и закрытые маршруты ЛК                              | Управление привязанными способами входа и доступом к данным своего участника программы |
| `packages/backend/src/orders/`              | Создание, расчёт и выгрузка заказа                          | Использование согласованных операций лояльности, сохранение снимка расчёта             |
| Планируемый `packages/backend/src/loyalty/` | Адаптер источника баланса, сопоставление клиента и операции | Отдельно чтение и изменение; точный внешний протокол после обследования                |
| Согласованные исходники витрины             | Экран входа, профиль, заказы и бонусы                       | Сначала базовый ЛК, затем бонусы и оформление с бонусами                               |

При внешнем входе сохраняем пару «провайдер + постоянный внешний ID», связанную с внутренним аккаунтом. Бонусная привязка хранится отдельно: источник/программа + постоянный ID участника. Телефон используется для подтверждённого первичного сопоставления, а не как единственный постоянный ключ всех операций.

В `orders` уже есть `bonus_amount` и `loyalty_account_ref`. Первое поле хранит денежный эквивалент применённых бонусов; курс бонуса не предполагается равным одному рублю. Отдельные записи операций должны хранить внешний ID, заказ, тип, сумму/единицы, ключ повторяемости и состояние сверки. Набор состояний определяется фактическим протоколом программы.

Основной баланс остаётся во внешней системе, установленной при обследовании. На сайте допустим кэш для показа с временем обновления; сохранённое значение не является основанием для нового списания без актуальной проверки.

Номера новых миграций назначаются после сверки веток: `019_accounts.sql` уже существует локально. Старые миграции и согласованные схемы не переписываются.

- [ ] Реализовать постоянную привязку внешнего ID к внутреннему аккаунту, сценарий недоступного телефона и предотвращение дублей аккаунтов.
- [ ] Проверить привязку второго способа после подтверждённого входа в существующий аккаунт; не раскрывать заказов другого пользователя.
- [ ] Проверить резервный вход и ограничения отправок; вход по резервному каналу открывает тот же аккаунт.
- [ ] Доставку реальных сообщений проверить после подключения сервиса и согласования тестовых номеров. Зафиксировать фактическую стоимость и ограничения.
- [ ] Описать фактические новые маршруты и правила привязки в документации; не выдавать проектируемый контракт за реализованный.

**Готовность:** на тестовом окружении пользователь проходит выбранный рабочий вход, повторно попадает в тот же профиль и имеет резервный способ доступа. Без телефона аккаунт не обходит инвариант первой версии.

### Этап 3. Интерфейс и выпуск базового кабинета

**Область:** согласованные исходники витрины; API из `docs/account-api.md`. Конкретный список файлов определяется после подтверждения источника витрины, до начала редактирования её кода.

- [ ] Встроить вход из меню «Профиль», выбор способов, состояния ожидания, ошибки и повторный запрос.
- [ ] Добавить профиль, список заказов, детали заказа и выход; телефон пока не редактируется.
- [ ] Подставлять данные аккаунта в оформление, позволяя проверить их перед отправкой. Заказ сохраняет собственный снимок контактов и доставки.
- [ ] В авторизованном сценарии отправлять заказ в `POST /api/account/orders`, в гостевом — в `POST /api/orders`.
- [ ] Проверить мобильную и настольную версии, обновление страницы, истечение сессии, пустую историю и отказ провайдера.
- [ ] Проверить, что гостевые заказы с тем же телефоном не появляются в кабинете.
- [ ] Выпустить базовый ЛК после проверки конфигурации рабочего окружения и выбранного входа.

**Готовность:** покупатель входит, видит и изменяет разрешённые данные, оформляет новый заказ и видит его в своём кабинете. Гостевая покупка сохраняется. Зависимости от готовности бонусной интеграции нет.

### Этап 4. Привязка участника и показ бонусов

**Файлы:** создать модуль `packages/backend/src/loyalty/` с доменными типами, сервисом сопоставления и адаптером согласованной внешней системы; добавить миграцию привязок участников, тесты модуля и документ `docs/loyalty-api.md`; дополнить `packages/backend/src/account/plugin.ts` и экраны ЛК.

- [ ] Сначала проверить отсутствие участника, одно совпадение, несколько совпадений, недоступную систему и попытку чтения чужого участника.
- [ ] Сопоставлять клиента по подтверждённому телефону, затем сохранять устойчивый внешний ID. Регистрацию нового участника реализовать только по согласованному правилу.
- [ ] Показывать отдельно доступные бонусы, ожидающие начисления, уровень и оборот — только те показатели, которые реально доступны.
- [ ] Добавить условия уровня, историю и сроки ближайшего сгорания, если источник предоставляет эти данные.
- [ ] Показывать время обновления; при ошибке не подменять баланс нулём. Для кешированных данных явно обозначать их актуальность.
- [ ] Сверить показ на сайте с системой заказчика на тестовых клиентах разных уровней.
- [ ] Выпустить чтение бонусов отдельным результатом, до возможности списания.

**Готовность:** аккаунт однозначно связан с действующим участником, покупатель видит корректные данные. Повторное связывание не создаёт дубль участника, чужие сведения недоступны.

### Этап 5. Списание, начисление и расчёт заказа

**Файлы:** расширить `packages/backend/src/loyalty/`, добавить журнал операций и миграцию; изменить `packages/backend/src/orders/service.ts`, `packages/backend/src/orders/pg.ts`, `packages/backend/src/orders/types.ts`, интеграцию оплаты и обмена только в подтверждённом объёме; дополнить контракт и оформление заказа.

- [ ] Утвердить исполнителя каждой операции: сайт, 1С либо CRM. Уже выполняемое кассовой системой действие сайт повторно не инициирует.
- [ ] Сначала добавить сценарии недостаточного баланса, изменившегося лимита, параллельной покупки на кассе и повторного запроса.
- [ ] На сервере рассчитывать допустимое списание и итог; сумма из браузера не определяет разрешённое количество бонусов.
- [ ] Использовать резервирование, подтверждение и освобождение, если они поддерживаются. При отсутствии резерва до запуска согласовать проверяемый механизм предотвращения двойного списания.
- [ ] Для онлайн-оплаты определить действия при создании платежа, успешной оплате, отказе и истечении срока. Для оплаты при получении отдельно определить момент списания и начисления.
- [ ] Связать внешние операции с заказом и устойчивыми ключами. Повтор HTTP-запроса, платёжного уведомления или обмена с 1С не создаёт новую бонусную операцию.
- [ ] При тайм-ауте с неопределённым результатом сначала выяснять статус операции по её ID/ключу; не повторять списание вслепую.
- [ ] Сохранять денежный эквивалент, единицы бонусов и правила расчёта, необходимые для дальнейшей сверки и возврата.

**Готовность:** сайт и касса используют согласованный основной баланс, начисление и списание происходят по определённым событиям ровно один раз. Существование реквизита «Бонус» в выгрузке 1С само по себе не подтверждает операцию во внешней системе.

**Зависимости:** онлайн-сценарий требует отдельно работающей интеграции оплаты (F4), а события получения/возврата — согласованного достоверного источника из 1С или другого серверного процесса. В текущем API наличие полей статуса ещё не означает приём событий оплаты и статусов из 1С (F3). Изменение состояния из браузера не запускает начисление. Если источник события не готов, соответствующая ветка бонусных операций не выпускается; чтение баланса и базовый ЛК продолжают работать.

### Этап 6. Отмены, возвраты, сверка и выпуск операций

**Файлы:** модуль лояльности и журнал операций, обработчики событий заказа/оплаты/1С, соответствующие тесты; создать `docs/loyalty-operations.md` с порядком сверки и устранения расхождений.

- [ ] До запуска списаний проверить отмену до/после оплаты, истёкшую оплату, освобождение резерва и полный возврат.
- [ ] Проверить частичный возврат: восстановление использованных бонусов, отмена начисленных, влияние на оборот и уровень — по правилам заказчика.
- [ ] Проверить покупку с бонусами одновременно на сайте и кассе, задержанные и повторные события, сбой между подтверждением оплаты и обновлением бонусов.
- [ ] Добавить сверку операций, состояние «требуется проверка» и повторную обработку только безопасных действий.
- [ ] Описать действия при недоступности системы: новые списания отключаются; оформление без бонусов требует подтверждения покупателем пересчитанного итога.
- [ ] Предусмотреть отключение новых бонусных операций без остановки завершения и сверки уже принятых.
- [ ] Провести сквозную приёмку с заказчиком: сайт → платёж/получение → 1С/CRM → баланс → отмена/возврат.

**Готовность:** успешная приёмка включает весь жизненный цикл покупки. Выпуск операций не выполняется после одного теста успешного списания без проверки возвратов.

## 8. Проверки и выпуск

Для каждого изменения серверного поведения сначала добавляются проверки ожидаемого результата, затем реализация и повторный запуск. Тесты должны проверять права доступа, расчёты, повторяемость и восстановление после сбоя.

Базовые команды из корня репозитория:

```bash
npm run build -w @fa/backend
npm run lint
npm test
```

Ожидаемый результат: успешное завершение каждой команды. Пропущенные тесты указываются отдельно и не считаются проверкой интеграции.

PostgreSQL-проверки текущей основы на отдельной тестовой базе с установленным `TEST_DATABASE_URL`:

```bash
npm test -w @fa/backend -- test/auth-pg.test.ts test/account-orders-pg.test.ts test/orders-pg.test.ts test/orders-export-pg.test.ts --no-file-parallelism
```

Ожидаемый результат: проверки PostgreSQL действительно выполнены, включая принадлежность заказов, гонки авторизации и прежнюю выгрузку в 1С. По мере добавления лояльности список расширяется её интеграционными проверками.

Внешние ID проверяются на тестовых приложениях и реальных разрешённых сценариях; бонусная система — в тестовом контуре или согласованных тестовых аккаунтах с проверкой результата на кассе. Подключение интерфейса требует браузерной проверки сквозного сценария.

Три независимых результата приёмки:

1. **Базовый ЛК:** рабочий вход, профиль, новый заказ, гостевой сценарий.
2. **Чтение бонусов:** правильный участник, баланс/уровень, актуальность и состояния ошибок.
3. **Операции:** списание, начисление, параллельная касса, отмены, возвраты и сверка.

## 9. Рассмотренные альтернативы входа и ориентиры расходов

Это материалы для выбора, а не обязательный набор функций. Публичные тарифы обсуждались 02.11.2026; перед договором они проверяются заново. 500 отправленных запросов/кодов не равны автоматически 500 успешным входам; повторы и резервные каналы могут увеличить расходы. Стоимость разработки и сопровождения отдельна.

| Способ                             | Ориентир и особенность                                                                                      | Роль в плане                                     |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| SMS от общего имени                | Для основных сетей через SMSPILOT 8,25–11,44 ₽ за короткий код; около 4,1–5,7 тыс. ₽ за 500 SMS             | Кандидат базового/резервного входа               |
| Яндекс ID                          | Яндекс заявляет оплату авторизационных уведомлений со своей стороны; телефон запрашивается отдельным правом | Приоритетный кандидат внешнего входа             |
| VK ID                              | SDK предусматривает запрос телефона/email; коммерческие условия и доступ к данным ещё проверяются           | Кандидат после проверки подключения              |
| Telegram Login                     | Бесплатная платформа входа; подтверждённый телефон передаётся с согласия пользователя                       | Рассмотренная альтернатива внешнему ID           |
| Telegram Gateway                   | Опубликовано $0,01 за доставленный код; нужен резервный канал                                               | Рассмотренная альтернатива доставке SMS          |
| Flash Call                         | SMS.RU публикует 0,40 ₽ на российский номер; 500 запросов — 200 ₽ до повторов/резерва                       | Возможен отдельный пилот; меняется сценарий кода |
| Wait Call                          | Покупатель сам звонит на выданный номер; тариф для магазина уточняется                                      | Дополнительный вариант, не основной по умолчанию |

| Passkey                            | Вход ключом устройства без сообщения при каждом входе; требуется первоначальная привязка и восстановление   | Дальнейшее развитие                              |

Доля использования ID неизвестна; это расчёт сценария, а не обещание экономии. Для VK в расчёт отдельно включаются подтверждённые при подключении коммерческие условия.
